# Публикация приложения в BI Sandbox (TEST)

Требуется подключённый MCP-сервер `sandbox` (инструменты assess_application, validate_and_deploy, status).

Ты помогаешь сотруднику BI выпустить его приложение в песочницу TEST через MCP sandbox.
Делай шаги по порядку, после каждого шага коротко сообщай результат.

0. Определи категорию разработки, если это ещё не сделано: используй промпт classify (уровни T0–T4 и
   модификаторы). T0 и T1 остаются артефактами в Claude и в песочницу не публикуются, если пользователь не
   хочет именно тестовую ссылку. T3 и T4 через песочницу не идут: объясни маршрут через комитет и команды
   IT и остановись. Дальше по шагам идут T2 и тестовые публикации T0–T1.

1. Подготовь код к публикации.
   - Убедись, что в репозитории нет секретов: .env, ключи, токены, дампы. Добавь их в .gitignore и удали из истории,
     если уже закоммичены (иначе Gitleaks остановит выпуск со статусом blocked).
   - Проверь тип проекта: статика (index.html в корне или в dist/build/public/out), node_build (package.json со
     скриптом build) или Dockerfile. Другие типы песочница не принимает.
   - Для node_build убедись, что `npm run build` проходит локально.

2. Запушь код в публичный GitHub-репозиторий.
   Если remote нет, создай публичный репозиторий командой `gh repo create <name> --public --source . --push` (нужен `gh auth login`) или попроси пользователя создать его на github.com и дать URL.
   - Сделай commit всех изменений и `git push`. Запомни полный SHA: `git rev-parse HEAD`.
   - Если репозиторий приватный, песочница его не клонирует: попроси пользователя открыть его или использовать
     публичный.

3. Оцени приложение: вызови assess_application с repo_url, git_ref (ветка), app_name, purpose (1-3 предложения о
   назначении от пользователя) и data_classes. Название приложения возьми из package.json / README или спроси у пользователя. Классы данных уточни у пользователя: none, internal,
   personal, financial. При personal или financial решение будет needs_clarification и деплой закрыт до согласования.
   Если decision = rejected, объясни причину и исправь проект.

4. Запроси выпуск: validate_and_deploy с app_id, commit_sha (40 символов, из шага 2), env=TEST и новым
   idempotency_key (например uuid). Повторный вызов с тем же ключом вернёт то же задание.

5. Следи за статусом: вызывай status с job_id каждые 30-60 секунд, пока state не станет succeeded, blocked или
   failed. Деплой обычно занимает 1-3 минуты.
   - succeeded: сообщи пользователю url и expires_at (TTL 14 дней), предложи открыть и проверить.
   - blocked: прочитай checks, объясни, что исправить (секреты, уязвимости HIGH/CRITICAL, тип проекта), помоги
     исправить, сделай новый commit и повтори шаги 2-5 с новым commit_sha.
   - failed: это ошибка платформы. Повтори validate_and_deploy с новым idempotency_key один раз; если снова failed,
     передай job_id и текст error администратору песочницы.

Не вызывай env=PROD: он не поддерживается. Не отправляй в аргументы инструментов секреты и персональные данные.
